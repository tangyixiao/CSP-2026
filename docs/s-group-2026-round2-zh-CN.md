# CSP-S 2026 第二轮：大表、小样例和输出补丁 / Big tables, small samples and output patches

> 一篇关于 2026 年 CSP-S 第二轮选手提交的长文。全部断言以归档内的文件、官方测试数据和官方题面为准，证据档见文末。
>
> A long-form piece on the Round 2 CSP-S 2026 contestant submissions. Every claim is grounded in archived files, the official test data and the official statement; the evidence record is linked at the end.

CSP-S 2026 第二轮的四道题是「能量水晶」（crystal）、「地铁」（subway）、「迁徙」（migrate）和「研发基地」（hub）。官方赛后公布了 180 对测试数据（crystal 20、subway 25、migrate 25、hub 20），这批数据在归档里可以直接读；而**题面原件也在归档里**——以一份 178,163 字节 PDF 的形式，被当成「研发基地」的源码交了上来。

有了题面和测试数据，「选手在文件里做了什么」第一次可以完全对齐着说：他抄的是哪一份答案、那份答案属于样例还是测试点、抄的时候漏了什么。

本文只写 S 组，取 61 份文件做样本。这不是普查，是选样：全组 114,658 份源码（八个源码扩展名，见第五章），正文读到的每一份都给出路径与 blob 指纹。

## 证据口径

四个标签，从硬到软：

| 标签 | 含义 |
| --- | --- |
| `[字节]` | 两个文件逐字节相同，或同一段内容 sha1 相同。可复现，不需要解释。 |
| `[逐值]` | 按整数 token 逐个比对，序列相同，或指出第几位不同。 |
| `[文本]` | 题面、注释、日志的原文，逐字引用。 |
| `[推断]` | 由代码反推、题面没写、也没实际运行过。凡标这个，正文会说清推的是什么。 |

三条自我限制，先写在前面：

1. **不评动机。** 一份表对上了样例答案，只说明这份表输出的正是那份样例的输出。它从哪里来、为什么在那里，本章不下判断。
2. **不把相似度当结论。** 字节相同、逐值相同、token 相同但分隔符不同，三件事分开报。
3. **数字都带口径。** 分母多少、按什么过滤、用的哪次提交，都写在句子里。

## 一、subway：25 份文件、23.80 MiB，和一组不在参数域里的键

subway 是这组题里最能直接拿体积说话的：归档里 S 组 `*/subway/subway.cpp` 共 **29,384 份 / 106,058,116 B**。本章取 25 份，合计 24,954,943 B（23.80 MiB），占 S 组全部源码字节（114,658 份 / 324,291,623 B）的 7.70%——**0.022% 的文件占 7.70% 的字节**。

这 25 份里有 13 份越过题面的源文件上限。题面注意事项第 4 条原文是「选手提交的程序源文件大小不得超过 100 KiB」（题面文本 L32）。按 102,400 B 计，全 S 组有 54 份源码越线，占 S 组源码总字节的 65.22%；其中 subway 33 份，是四道题里最多的一道（另有 hub 12、crystal 5、migrate 3，还有一份落在 `HN/S/HN-S00678/1.cpp` 这种非四题目录的路径上）。`[字节]` 这 25 份里体积最大的是 `JS/S/JS-S01159/subway/subway.cpp`，8,810,819 B，86.0 倍；全 S 组 subway 里还有更长的，`GD/S/GD-S04435/subway/subway.cpp` 11,213,149 B，不在本章 25 份内。题面本体在归档里，只是形态特殊：`JS/S/JS-S00009/hub/hub.cpp` 不是代码，是一份 178,163 B 的 PDF（`%PDF-1.7`），提取成纯文本，行号即下文引用的「题面文本 L…」；subway 的输入格式、数据范围、样例 1–2 与样例 3–7 各自满足的测试点，都在这份文本里 `[文本]`。下面凡引用参数含义，出处都是它。

### 官方把 25 个测试点钉死了，选手把键钉在另一套数上

题面第二页给出输入第一行的五个字段：`c, n, m, d, q`，分别是测试点编号、地铁线路数、地铁站数、每个地铁站最多被几条线路经过、出行计划数；「特别地，若 `c = 0`，则该测试点为样例」（题面文本 L177–179）。数据范围是 `1 ≤ n ≤ 500`、`1 ≤ m ≤ Σki ≤ 5×10⁵`、`1 ≤ d ≤ 20`、`1 ≤ q ≤ 10⁵`（题面文本 L327）。`[文本]` 把官方 25 个 `.in` 的首行逐个读出来（`test-data/S/official/subway/subwayN.in`，N=1..25），实际用到的是：`c` 恒等于组号 1..25；`n ∈ {3, 15, 195, 495, 1, 2}`；`m ∈ {7, 8, 72, 132, 192, 193, 493, 19302, 490542, 495492, 495495, 499999, 500000}`，最大 500000；`d ∈ {20, 2}`；`q ∈ {10, 200, 2000, 100000}`。`[逐值]`

而本章 25 份文件里写进条件的键是另一套：`n=480`、`m=481`、`m=18721`、`m=479521`、`q=90000`。这几个数在官方 25 组首行里一个都不出现——`n=480` 不违反 `n ≤ 500`，但没有任何一个测试点用它；`q=90000` 同理落在 `q ≤ 10⁵` 之内，却不在官方用到的四个 `q` 值里。`[逐值]` 两处撞车要说清楚，否则后面的数字会被误读。第一，`n=2/3/15` 和 `d=2`、`q=200/2000` 本身**是**官方用到的值，所以单列条件命中的情况很常见：`if(n==3)` 会同时命中官方第 1、2、3 组，`if(d==20)` 会命中 23 组。第二，七组样例键里没有一组与官方任何一组的四元组完全相同（`exact=[]`），最近的是样例 2 的 `(3,7,20,2)` 与官方第 1、3 组的 `(3,7,20,10)`——四个字段里前三个一样，只有 `q` 不同。`[逐值]` 也就是说：这些键不难在单列上撞到官方，但作为一个四元组，一个都没撞上。

### 三个巨串：与官方答案的最长共同连续段是 2 个值

拿官方 25 组 `.ans` 的全部十进制 token 建 3-gram（distinct 1,303,631 个），扫本章 25 份文件的全部 token：**每份命中 0 次，合计 0**。等价说法是：任何一份文件与任何一组官方答案，最长共同连续段不超过 2 个值。`[逐值]` 同一扫描里，25 份中「完整包含某组官方答案」的份数是 0。`[逐值]`

所以本章所有关于「值」的对照，都必须换成另一把尺子。归档里恰好有这把尺子：GX 省 9 份提交把整个工作目录交了进来，九份 subway 目录下都有七份样例答案 `subway1.ans`…`subway7.ans`，其中八份同时留着 `subway.cpp`（`GX-S00194` 只有答案和可执行文件，源码没交）——`GX/S/GX-S00126`、`GX-S00149`、`GX-S00194`、`GX-S00514`、`GX-S00544`、`GX-S00554`、`GX-S00569`、`GX-S00588`、`GX-S00594`。`[字节]` 七份样例答案的规模是：`subway1.ans` 2 值（`32`/`17`）、`subway2.ans` 2 值（`35`/`16`）、`subway3.ans` 200 值、`subway4.ans` 90,000 值、`subway5.ans` 2,000 值、`subway6.ans` 90,000 值、`subway7.ans` 90,000 值。`[逐值]` 而题面里七份样例各自满足的测试点是：样例 3 → 4~6，样例 4 → 9~11，样例 5 → 12~15，样例 6 → 16~19，样例 7 → 22,23（「题面文本 L291」）。`[文本]`

把样例键和官方那几组的首行摆在一起，差距就一句：**同量级，不同值**。样例 4 的键是 `(480, 481, 20, 90000)`，对应的官方 9~11 组是 `(495, 493, 20, 100000)`；样例 5 键 `(480, 18721, 20, 2000)` 对官方 12~15 的 `(495, 19302, 20, 2000)`，只有 `q` 相同；样例 7 键 `(480, 479521, 2, 90000)` 对官方 22、23 的 `(495, 495495, 2, 100000)`，只有 `d=2` 相同。`[逐值]` 样例 1、2 的键可以直接用题面钉：`0 2 5 20 2` 与 `0 3 7 20 2`（题面文本 L207、L253），去掉 `c=0` 就是 `(2,5,20,2)` 与 `(3,7,20,2)`——`HB-S00624`、`HA-S00294` 等文件里的条件与此逐位相同。`[文本]` 这一条同时说明了键的读法：**键就是样例输入文件的第一行**。样例 3–7 的 `.in` 不在归档里，但那七组键与七份样例答案一一嵌合，形态上只能是同一件事。`[推断]`

四个数字把整章的量级钉住：25 份文件里 **21 份**携带至少一份样例答案，**5 份**七份全带（`AH-S00871`、`HA-S00294`、`JS-S01159`、`GZ-S00439`、`HB-S00624`），**0 份**携带任何一组官方答案，携带实例合计 96 次。`[逐值]` 这 96 次里有 **54 次**写成单个完整字符串字面量；其余 42 次的 token 在源码里同样连续，只是由相邻的多条 `cout` 逐行拼出。把那 54 次按 C++ 转义还原后与 `.ans` 比字节：**25 次逐字节完全相同**，7 次只差 `\n` 与空格，22 次只是 token 序列相同而分隔符与折行组合不同。`[字节]`

### 七支分支，死在第十七个 if 的一个右括号

**`HB/S/HB-S00624/subway/subway.cpp`**（blob `2ea06e64e138`，2,278,155 B / 21 行）是这七组键写得最完整的一份：五列全写，`n`、`m`、`d`、`q` 全部落在条件里，七支分支一支不少，第 11–17 行一支一行的 `if`。前 10 行（含两个 `freopen` 与五参读入）没有任何问题。

### 一份表后面接着一份完整的 Floyd

**`AH/S/AH-S00871/subway/subway.cpp`**（blob `40eaaa959044`，2,283,420 B / 82 行）有两个别处没有的东西。第 28 行是一条**负条件**：`if(c==0&&n==480&&d==20&&m!=481){` ——本章唯一一条用 `!=` 写的键，意思是「`n=480` 且 `d=20`，但不是 481 那组」。`[文本]` 第 29 行是它自己的旧版：整行以 `//` 开头，被注释掉的 900 个值，首 token 是 `//		cout<<"97\n905\n426\n361\n290\n471\n…`，与第 30 行启用版的 90,000 值前 900 个逐值相同。`[逐值]` 旧版比新版短两个数量级，看得出是先试了 900 个数、后补成全量。

更值钱的是第 42–80 行：这不是表，是一份真算法。第 43–47 行读 `w[i]` 并把站厅时间并进 `floyd[0][i]`；第 48–67 行逐条线路读入，用 `if(tmp==0){…A=a;T+=t;}else{floyd[A][a]+=T;}` 把线路上相邻两站连边、并把同线内的时间累加；第 68–75 行标准 Floyd 三重循环；第 76–80 行按 `cout<<floyd[x][y]` 输出 `q` 组询问。`[文本]` 也就是说：**表没命中的输入，它会给一份完整答案。** 这一点全章只有它和 `HA-S00294` 的 `else` 做到。

### 非样例输入时，它把测试点编号打了出来

**`HA/S/HA-S00294/subway/subway.cpp`**（blob `142605db9509`，2,278,793 B / 47 行）的兜底是本章最省力的一行：第 43 行 `}else{`，第 44 行 `cout << c;`。`[文本]` 官方 25 组的 `c` 恰好是 1..25，所以这一行在官方评测里的输出是测试点编号本身。

它的读入倒是这 25 份里最完整的一份：第 11–13 行读 `m` 个 `w`，第 15–21 行读 `n` 条线路的 `k[i]` 与 `(a,t)`，第 23–25 行读 `q` 组询问，全部落在 `t[490][480000]`、`a[490][480000]` 两个数组里。`[文本]` 这两个数组的声明在同一个第 4 行上：`int w[500010],k[510],t[490][480000],a[490][480000];`。它们本身是个问题：单个 490×480000 的 `int` 占 940,800,000 B，即 897.2 MiB；两个加 1,794.4 MiB = 1.75 GiB，而题面给的内存限制是 1024 MiB（题面文本 L12）。`[字节]` 它维护好读入结构的代价，是这份程序在读到第一个 `w` 之前就已经放不下——这是本章 25 份里唯一一处「代码形态正确但资源预算不成立」。

## 四、migrate：四道题里唯一把官方答案逐值抄进 `cout` 链的题型

四道题里，migrate 被放在最后写，理由只有一个：只有它，一段 `cout` 链里就能整整齐齐躺着十几个按行排好的整数，形态和官方 `.ans` 一模一样。四题的官方答案体量差得极远——`.ans` 里一行一个数数过去，crystal 恒为 1 个数，hub 3 到 5 个数，subway 从 10 个到 100,000 个数，migrate 从 2 个到 33,334 个数。只有 migrate 的答案小到可以整段抄进 `if` 分支，又长到足以逐字节认人。

于是两件事撞在了一起：**官方数据里本来就有三组答案逐字节相同**，而选手文件里又确实完整躺着那几组值。它被拿来压轴，不是因为抄得多，而是因为抄下来的东西本身就是一个可以逐字节比对的证物。

本章所有「与官方是否相同」的判断都只到字节层和逐值层，不评动机，也不构成任何性质判定。

### 题面在归档里，出处不止一处

migrate 的题面出现过两次。第一次是选手抄进去的：`GD/S/GD-S03636/crystal/crystal.cpp`（54,300 字节 / 54 行，blob `8296cab25309`）第 37–54 行是一段 `/* … */` 注释，逐字贴了整份 S 组试卷的文本，带「第 8 页 共 13 页」这种页码残留。第 48 行含 migrate 的【输入格式】整段。

第二次是试卷本体：`JS/S/JS-S00009/hub/hub.cpp`（178,163 字节，blob `76d1f4cfdd14`）是一份 13 页的真 PDF，被当成源码交了。`pdftotext -layout` 之后是一份提取出的纯文本（27,703 字节），migrate 题面在 L361–520。两份文本互校一致，下面全部引自后者 `[文本]`：

- 第一行两个非负整数 `c, t`，`c` 是测试点编号，`t` 是测试数据组数；**「特别地，若 c = 0，则该测试点为样例」**。
- 接下来 `t` 组，每组第一行 `n, d`（岛屿数量、海鸟一次最多能飞行的距离），第二行 `n` 个严格递增的整数（岛屿坐标）。
- 输出到 `migrate.out`，每组一行一个非负整数。

所以选手表里那个四列键 `(c, t, n, d)`，就是输入前四行的前四个数。而几乎所有表都把条件写成 `c==0`——因为**样例是用 `c=0` 跑的**。这一句和题面那句「若 c = 0，则该测试点为样例」严丝合缝，也解释了为什么这些表看起来「完全正常」：它们本来就是「当这是一次样例运行时，请输出这些行」的程序。

同一段文本还给出了样例与测试点的对应关系，这是本章后面所有数字的枢纽：

| 样例 | 题面原话 | 官方测试点 |
| --- | --- | --- |
| 样例 3 | 见题目目录下的 `migrate/3.in` 与 `migrate/3.ans`。该样例满足测试点 3 ∼ 6 的约束条件。 | 3–6 |
| 样例 4 | 见题目目录下的 `migrate/4.in` 与 `migrate/4.ans`。该样例满足测试点 11, 12 的约束条件。 | 11, 12 |
| 样例 5 | 见题目目录下的 `migrate/5.in` 与 `migrate/5.ans`。该样例满足测试点 15 ∼ 18 的约束条件。 | 15–18 |
| 样例 6 | 见题目目录下的 `migrate/6.in` 与 `migrate/6.ans`。该样例满足测试点 19 ∼ 21 的约束条件。 | 19–21 |

也就是说，**出题人自己声明了样例 3 和样例 6 与官方测试点是同一批约束条件**。这句话后来解释了为什么会有逐字节相同的答案。

### 官方数据自己就有大批同答案的测试点

先把官方的重复讲清，否则后面所有的「撞上官方」都会被误读成撞上了稀有事件。

官方 migrate 25 组答案里，有三个集合是**逐字节完全相同**的：

| --- | --- | --- |

| 7 / 8 / 9 / 10 | 52 | `b9814ba8a92e` |

第 3/4/5 组都是那 17 个值：`8129 16 9 7 12 0 0 0 2 1 0 2 3 6 0 2 0`；第 19/20/21 组都是那 16 个值：`6800625333 6247500 6242502 4998 9994 0 0 0 2 1 0 2 3 6 0 2`。

### 所以这一章到底在说什么

## 六、样例：一份 1.7 MB 的「草稿」，装着五组样例的输入和两份答案

上一章最后提到 `ZJ/S/ZJ-S00872/hub/caogao.cpp`：1,715,345 字节，497 行，非空行全是纯整数，没有一行代码。这一章专门把它拆开，因为在本次扫描的归档里，它是唯一一份能独立佐证「样例长什么样」的东西。

先说为什么这件事重要。这一场 S 组的题面（`JS/S/JS-S00009/hub/hub.cpp` 那份 PDF）只完整印了每题的前两个样例，样例 3 及以后全部写成「见题目目录下的 `<题>/N.in` 与 `<题>/N.ans`」。而选手们抄的是样例——前面几章已经数过：subway 25 份里 21 份携带样例答案，hub 10 份里 10 份全带。所以「样例的输入到底长什么样」直接决定了能不能判断一份文件抄的是哪一份样例、抄得对不对。

归档里没有任何 `<题>/N.in`。`git ls-tree -r` 全库扫 `.in$`，除 `test-data/` 之外零命中。也就是说，样例的**输入**在归档里一份都没有。样例的**答案**只剩一处来源：九份把整个工作目录交上来的 GX 提交（`GX-S00126`、`GX-S00149`、`GX-S00194`、`GX-S00514`、`GX-S00544`、`GX-S00554`、`GX-S00569`、`GX-S00588`、`GX-S00594`），各带 11–22 份 `.ans`；本章引用的是 `GX-S00126` 那一份的 22 个文件。
而 `ZJ-S00872/hub/caogao.cpp` 把输入和答案一起装进来了。

### 它的结构

按空行切段，497 行是八段：

| 行区间 | 行数 | 首行 | 这是什么 |
| --- | --- | --- | --- |
| L1–L2 | 2 | `500000 19768503` | crystal 样例 4 的输入（首行 + 50 万个 `a_i`） |
| L4–L8 | 5 | `0 2` | migrate 样例 1 的输入（与题面逐行相同） |

八段里，输入和答案混着放，前后顺序也不对应题面顺序。它不是一份程序，是一个人在考场里把样例一组一组抄下来、答案贴着输入一起存的草稿。文件名 `caogao` 直译就是「草稿」。

### 三处硬核对

这份草稿的价值在于它能和别的证据对上。三处都核过了：

**第一，subway 样例 3 的答案逐值相同。** `caogao.cpp` L70–L269 的 200 个整数，与 `GX/S/GX-S00126/subway/subway3.ans` 的 200 个值**逐值完全相同**，首值 `341`、第二值 `667`。

**第二，migrate 样例 3 的答案逐值相同。** L11–L27 的 17 个整数与 `GX/S/GX-S00126/migrate/migrate3.ans` 逐值完全相同：`8129 16 9 7 12 0 0 0 2 1 0 2 3 6 0 2 0`。这 17 个值同时也是官方第 3、4、5 组的答案——官方这三组本来就同答案，这是后面要专门讲的一件事。

**第三，crystal 样例 4 的首元素被单独证实。** L1 是 `500000 19768503`，L2 是 50 万个 `a_i`，第一个是 `61`。而 `QH/S/QH-S00045/crystal/crystal.cpp` 里那条三列键写着 `a==500000 && b==19768503 && c==61`，指向答案 `315275`。此前我只能说「第三个键位看起来像数组首元素」`[推断]`；现在草稿里的原始数据摆着第一个元素就是 `61`，这一条升为 `[逐值]`。

顺带两个新数字：这 50 万个 `a_i` 的最小值是 `-100`、最大值是 `100`，取值上下沿都能看出来；而最后一个值是 `70`。

### 两段输入都是完整的

`caogao.cpp` 里那两段「输入」不只是开头抄了几行，是一行不缺的完整文件。这一点值得单独验，因为它决定了这些数据能不能当真数据用。

**subway 样例 3**（L272–L488）：首行 `0 15 136 20 200`，`n=15` 条线路、`m=136` 个站、`q=200` 次查询。往下对：第二行正好 136 个站权；接下来 15 行是线路描述，每行以 `k` 开头、后跟 2k 个数（15 行的 `k` 全是 10，合计 150 段站内区间，逐行 token 数全部对得上）；再往下 200 行查询，每行恰好两个站号，首三行 `123 131` / `112 57` / `9 117`，末两行 `125 81` / `28 11`。**一行不多、一行不少。**

**migrate 样例 3**（L29–L63）：首行 `0 17`，往下 17 组，每组 `n d` 加一行坐标。解析器一组一组走完 17 组、坐标个数组组对得上、正好吃掉 35 行——**同样一行不多。**

也就是说这是一份能直接喂给程序的输入，不是摘要。它甚至比 GX 那九份提交更完整：那边只有 `.ans`，这边连 `.in` 一起。

### subway 样例 1：草稿少抄了一个数

L491–L496 是 subway 样例 1 的输入。和题面 PDF 印的那六行并排比，前五行逐字相同，最后一行不一样：

```
草稿   L491: 0 2 5 20 2       题面: 0 2 5 20 2
       L492: 4 1 9 2 5              4 1 9 2 5
       L493: 3 1 5 2 7 4 6          3 1 5 2 7 4 6
       L494: 3 2 3 3 4 5 7          3 2 3 3 4 5 7
       L495: 1 3                    1 3
       L496: 1 5                    1 2
```

题面写的是查询 `1 3` 与 `1 2`，输出 `32` / `17`。草稿写的是 `1 3` 与 `1 5`。

这一处差异本身不影响结论——`1 5` 也是合法查询（站号 ≤ 站点数），草稿就是一份手抄件，抄错一个数字很正常。但它值得写出来，因为它说明了这份草稿的性质：**它是人在考场里看着屏幕手抄的，不是程序导出的**。一个字的差错就是手抄的证据。

同一份草稿的 L66–L68 是另一处痕迹：`0 1` / `5 3` / `-3 0 2 3 4` —— `c=0`、`t=1`、一个 `n=5 d=3` 的测试组。题面的 migrate 样例 1 是 `t=2`（`4 2` 与 `5 2` 两组），样例 2 是 `t=2`（`5 3` 与 `6 2` 两组）。这里只有一组，坐标 `-3 0 2 3 4` 也不是任何一组样例的原文。它是自己编的一个小测试——大概是想拿 `migrate/2` 那组的一部分单独跑一遍。这份草稿里有一处自造数据，这是它作为「草稿」最直接的证据。

### 为什么它比题面还珍贵

题面 PDF 印了样例 1、2 的输入；样例 3 以后一律「见目录」。而 `caogao.cpp` 里有 **subway 样例 3 的完整输入**（217 行：首行 5 个参数、次行 136 个站权、15 行线路描述、最后 200 行查询）、**migrate 样例 3 的完整输入**（35 行、17 组）、**crystal 样例 4 的完整输入**（50 万个 `a_i`）。

这些输入在归档的其余部分一份都没有。也就是说：如果有人想核对「选手抄的那 200 个数到底是不是样例 3 的答案」，而不只是「这串数在 25 份文件里出现频率多高」，那么在本次扫描里，唯一的独立参照就是这份草稿。

前面 subway 那一章说「样例 3 的答案在不同文件里有四种不同的字节写法，值一样、字节不同」，判据是拿 `GX/S/GX-S00126/subway/subway3.ans` 当参照。现在这个参照有了第二份独立来源：`ZJ-S00872/hub/caogao.cpp` 的 L70–L269。两份都在，且逐值相同。

### 它同时暴露了一件事

`caogao.cpp` 被放在 `hub` 目录里，但不是 hub 的数据。它装的是 crystal、migrate、subway 三题的样例，一份 hub 的内容都没有。

同一个考号下另外还有五份正常提交：`crystal/crystal.cpp` 895 B、`hub/hub.cpp` 258 B、`migrate/migrate.cpp` 1,579 B、`subway/1.cpp` 2,031 B、`subway/subway.cpp` 1,975 B。

所以 `caogao.cpp` 是一份额外放进去的备份——把几组样例的输入和两份答案一起存起来，塞进了 hub 目录。它超了限额 16 倍（1,715,345 B / 102,400 B），但它不是「用体积说话」的那一类：它是真的把数据写全了，只是写错了地方。

超限的 54 份里，别的是在撑大小、卡评测、或者干脆交一张截图；这一份的动机在文件里写着——它想把手边的样例都存下来。这个区别不做价值判断：「诚实」不是能由文件本身证实的属性，能证实的只有一件事：它存的是数据，不是话。

### 这一章要说的一句话

前面几章反复讲「选手抄的是样例，不是测试点」。这个判断要成立，得有样例可以对照。题面只给两个，归档里一份 `.in` 都没有——按理说这条线是断的。

`caogao.cpp` 把它接上了。它是这场考试里最不起眼的一份文件：1.7 MB 纯数字，没有一行代码，没有一句注释，连标题都没有。但这 497 行恰好证明了那些 2 MB 的答案表抄的到底是什么。
